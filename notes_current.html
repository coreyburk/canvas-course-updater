Why Functions, Loops and Error Handling Matter

A script that works once on your machine and a script someone can maintain are different things. Functions give the work a name, loops stop you repeating yourself, and error handling decides what happens when a path is missing or a command fails at 3 AM with nobody watching. This lab asks you to build the same small report three times so you can see how each language expresses those three ideas, because the differences are real and you will choose between them for the rest of the course.

What You Are Being Graded On

Three scripts, one in each language, each gathering system information. The scripts are the vehicle; the four requirements below are what the rubric actually looks for.

Functions

At least two or three per script, with descriptive names. The test is whether the main body reads as a list of intentions rather than a wall of commands.

Loops

Each script must iterate over a collection rather than repeating the same block with different values. A list of paths is the obvious candidate.

Error Handling

Handle at least one real failure, such as a path that does not exist or a command that fails. Check before you use a result, and say something useful when it is not there.

Comments

One line above each function saying what it does. Cheap to write and the first thing a reader looks for.

Three Screenshots

Each script running successfully and producing its report. Label which is which.

The Written Comparison

100 to 150 words on four dimensions: function syntax, loop behavior, error handling, and which language felt most natural. Answer all four.

The Same Three Ideas in Three Languages

These are patterns to adapt, not the script you are writing. Get each pattern working on its own at the command line first.

Bash

# A function: no parameter list, arguments arrive as $1, $2 ...
# Returned DATA goes to stdout and the caller captures it.
describe_thing() {
  local name="$1"
  echo "value for $name"
}

RESULT=$(describe_thing "example")

# A loop over an array
items=("first" "second" "third")
for item in "${items[@]}"; do
  echo "checking $item"
done

# Error handling: test before you use, and provide a fallback
if [ -d "$path" ]; then
  echo "  $path: $(du -sh "$path" 2>/dev/null || echo 'N/A')"
else
  echo "  $path: ERROR - not accessible"
fi

Key: return in bash sets an exit status between 0 and 255, not a value, so a function returns data by echoing it. Declare function variables local or they are global and will overwrite your caller's variables. || runs the right-hand side only when the left-hand side fails, which is the shortest error handler bash offers.

PowerShell

# A function: Verb-Noun naming, typed parameters
function Get-ThingDescription {
  param([string]$Name)
  "value for $Name"
}

$Result = Get-ThingDescription -Name "example"

# A loop over an array
$items = @("first", "second", "third")
foreach ($item in $items) {
  Write-Host "checking $item"
}

# Error handling: test first, and catch what can still throw
if (Test-Path -Path $path) {
  try {
    # work that might fail
  }
  catch {
    Write-Host "  $path : ERROR - $($_.Exception.Message)"
  }
}
else {
  Write-Host "  $path : ERROR - path not found"
}

Key: Any value a PowerShell function leaves on the pipeline becomes its output, so an unassigned expression is effectively a return. Inside a double-quoted string, reaching a property needs $( ) around it, which is why the catch block above wraps the exception message that way. Test-Path is the cheap guard; try/catch is for what you cannot test in advance.

Python

import os
from pathlib import Path

# A function: named parameters, explicit return, docstring
def describe_thing(name):
    """Return a short description of the named thing."""
    return f"value for {name}"

result = describe_thing("example")

# A loop over a list
for item in ["first", "second", "third"]:
    print(f"checking {item}")

# Error handling: catch the specific exception you expect
for path in paths:
    try:
        if path.exists():
            print(f"  {path}: ...")
        else:
            print(f"  {path}: ERROR - path not found")
    except PermissionError:
        print(f"  {path}: ERROR - permission denied")

Key: A Python function with no return gives back None, and the error surfaces later somewhere confusing, so be explicit. Name the exception you expect rather than catching everything, because a bare except swallows your own typos too. Note that this lab needs no subprocess: platform, os and pathlib get the system information directly, which is faster and avoids parsing text.

Key Challenge: Three Philosophies of Failure

The hardest part of this lab is not writing three functions. It is that the three languages disagree about what should happen when something goes wrong, and that disagreement is exactly what your written comparison is asking about.

Bash assumes you are watching. A failed command prints to stderr and the script carries on to the next line. Nothing stops. You find out by checking the exit status yourself, which is what || and if [ $? -eq 0 ] are doing. The cost is that forgetting to check is silent.

PowerShell splits errors in two. Some stop the command, most do not, and only the first kind reaches a catch block. This surprises nearly everyone: a perfectly sensible try/catch can sit there doing nothing while a red error prints. If you want a cmdlet failure to be catchable, you generally have to ask for it with -ErrorAction Stop. You will meet this properly in Week 2; for now, notice when it happens.

Python stops by default. An unhandled exception ends the script and prints a traceback naming the file and line. It is the loudest of the three, which makes it the easiest to debug and the least forgiving if you wanted the script to continue.

Try this deliberately. Add a path to your list that does not exist, run all three scripts, and watch what each one does. One will carry on quietly, one may print red and continue anyway, and one will stop unless you caught it. That single experiment gives you most of your written comparison, grounded in something you actually observed rather than something you read.

Your Workflow: Build Each Script Incrementally

  1. Confirm your three environments - bash, PowerShell and Python should each run a one-line hello before you write anything real. Lab 1.1 set these up.
  2. Create the scripts directory - keep all three scripts together so the comparison at the end is easy.
  3. Write one bash function - something that returns a single value, such as the hostname. Call it and print the result. Nothing else yet.
  4. Add a second and third function - the rubric asks for two or three. Give each a comment line before you move on, while you still remember what it does.
  5. Add the loop - iterate over a list of paths rather than writing the same block three times. This is the requirement people most often miss.
  6. Add the failure case - put a path in the list that does not exist and make the script say so clearly instead of printing a raw error.
  7. Assemble the bash report - call your functions from the main body, redirect the output to a file, and take your screenshot.
  8. Port it to PowerShell - same three functions, same loop, same failure case. Notice where the structure maps across cleanly and where it does not.
  9. Port it to Python - same again. By now the third one should be quick, because you are translating a design rather than inventing one.
  10. Run all three side by side - confirm the reports say the same things, and capture the remaining screenshots.
  11. Run the failure experiment - break a path on purpose in all three and write down what each one did. This is your evidence.
  12. Write the comparison - 100 to 150 words covering all four dimensions: functions, loops, error handling, and which felt most natural. Cite what you observed in step 11.
